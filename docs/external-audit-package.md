# External audit package

**Status: no independent audit has been performed.** This page prepares the materials
an external reviewer would need. It is not evidence that a review happened, and the
project must not be described as independently audited until a reviewer has completed
one and published a report.

The internal audit is in `docs/security-audit.md`. It records the scope, controls,
tool results and residual risk, and it states its own limits.

## 1. Review target

- Project: NHI-Blast, version `0.1.1`, tag `v0.1.1` (the `v0.1.0` materials remain
  available for comparison). The source tree on `main` is 0.2.0 under a proprietary
  licence and has not been released; reviewers who prefer the exact released code
  should use the `v0.1.1` tag, which is the MIT-licensed release.
- Repository: `DKtech-dev/nhi-blast`, public at
  https://github.com/DKtech-dev/nhi-blast since 2026-10-27.
- Language and runtime: Python 3.12+; no runtime network access.
- Artifacts: `nhi_blast-0.1.1-py3-none-any.whl`,
  `nhi_blast-0.1.1.tar.gz` and `SHA256SUMS`, attached to the `v0.1.1` release.
- Source archive: the release tarball generated by the forge for the tag.

The tag, release assets and `SHA256SUMS` are authoritative. This document is packaged
inside the sdist, so it cannot contain the sdist's own digest without invalidating it.

## 3. Suggested review focus

1. **Parser safety.** Hostile YAML (aliases, duplicate keys, deep nesting, oversized
   files), malformed JSON/HCL, encoding edge cases, and whether diagnostics replace
   exceptions without losing partial facts.
2. **Path containment.** Traversal, symlinks, Windows junctions, case-insensitive
   paths and files added or replaced between discovery and read.
3. **Secret handling.** Whether a credential value can reach console, JSON, SARIF,
   HTML, diagnostics, logs or test goldens; whether Terraform sensitive values and
   expression results are handled conservatively.
4. **Report security.** HTML escaping, CSP and inline hashes, DOM construction,
   hostile strings in every string field, and whether embedded data can break out of
   the JSON block.
5. **Evidence honesty.** Whether UNKNOWN edges can affect R/E/Z, whether the weakest
   evidence class is used, and whether report prose overstates potential authority.
6. **Determinism and limits.** Set iteration, time, locale, path ordering and graph
   traversal; memory/CPU bounds on pathological inputs.
7. **Supply chain and release.** Lock integrity, action pinning, CI token exposure,
   artifact allowlists, build reproducibility and checksum handling.

## 4. Reproduction

The analysis runtime is offline. Tool installation may require network access in the
reviewer's environment; the tool itself must never make a network call.

```sh
python -m venv .venv
.venv/bin/python -m pip install --upgrade pip
.venv/bin/python -m pip install -c requirements.lock dist/nhi_blast-0.1.1-py3-none-any.whl
.venv/bin/python -m pip install -c requirements-dev.lock "dist/nhi_blast-0.1.1-py3-none-any.whl[dev,hcl,rich]"

.venv/bin/python -m pytest
.venv/bin/python -m pytest -m security
.venv/bin/python -m pytest -m slow
.venv/bin/python -m ruff check src tests scripts
.venv/bin/python -m mypy --strict src
.venv/bin/python scripts/check_coverage.py
.venv/bin/python scripts/gen_schema.py --check
.venv/bin/python scripts/check_artifacts.py dist
```

SBOM regeneration:

```sh
mkdir -p /tmp/sbom/runtime /tmp/sbom/dev
cp requirements.lock /tmp/sbom/runtime/requirements.txt
cp requirements-dev.lock /tmp/sbom/dev/requirements.txt
syft scan dir:/tmp/sbom/runtime -o cyclonedx-json=sbom-runtime.cdx.json
syft scan dir:/tmp/sbom/dev -o cyclonedx-json=sbom-dev.cdx.json
grype sbom:sbom-runtime.cdx.json
grype sbom:sbom-dev.cdx.json
```

On Windows use `.\.venv\Scripts\python.exe` and the corresponding script paths.

## 5. Ground rules

- Test fixtures contain synthetic credential-shaped strings. They are not real
  credentials and must not be reported as a leak. The same applies to the ignored
  research cache, which is not shipped.
- Do not include real credential values, customer repositories or private research
  material in a report. The project's reporting rules are in `SECURITY.md`.
- Treat a report generated from a hostile repository as sensitive: it may describe
  authority paths in that repository.
- The tool does not execute scanned content or contact cloud services. A review that
  requires execution of scanned content is out of scope.

## 6. Expected deliverable

A useful report states the commit reviewed, the environment, the method, each finding
with severity and reproduction, and which claimed properties held or failed. Findings
that are documented limitations or accepted assumptions should be distinguished from
defects. A retest statement after fixes is valuable; the project does not claim an
audit until that report exists.

## 7. Reporting and disclosure

Report vulnerabilities privately through GitHub private vulnerability reporting on the
repository, as described in `SECURITY.md`. Do not open a public issue. The project has
no bug bounty and no formal SLA.

## 8. What remains unverified

- Independent human review of the source, tests, reports and release process.
- Formal verification of the graph or policy evaluator.
- Runtime behaviour on platforms other than Windows 11, Ubuntu and Windows GitHub
  runners.
- Security of the hosting platform, the maintainer account and the reviewer's
  environment.
- Long-term maintenance, response times and backport policy beyond the `0.1.x` line.
