# Offline CI-to-Cloud Response: Evidence, Limits, and Product Choices

## Executive Summary

**Assessment date: 2026-11-03.** The useful product boundary is an evidence-constrained incident decision package, not a claim to reconstruct actual compromise from configuration alone.

- **Exposure Is Not Theft**: The **March 14, 2025** tj-actions investigation found secrets in public workflow logs, but no evidence of remote-network exfiltration -> distinguish possible access, observed exposure and confirmed use. [13]
- **Two Independent Credential Clocks**: GitHub job credentials and AWS STS sessions have different termination conditions; AWS role chaining can last **one hour** -> model session survival separately from CI cancellation. [1][19]
- **Graph Prior Art Is Substantial**: BloodHound already models GitHub workflows, secrets and relationships; OpenHound preserves collected data before conversion -> do not position offline graphs or reproducible collection as new. [3][10]
- **Permission Is Conditional**: `id-token: write` permits OIDC-token retrieval, not general resource writes; AWS session policies constrain role permissions -> explain each prerequisite rather than label a role simply reachable. [6][19]
- **Revocation Precedes Recovery**: AWS's role-session revocation denies older sessions but does not prevent later sessions -> close issuance paths before relying on revocation and rotation. [17]
- **Complement Established Tools**: Compare the **12 alternative families** below on evidence, temporal behavior and response workflow, not scanner counts. Release freshness, complete policy coverage and adoption remain unknown where not established.

## Incident Evidence Reveals the Actual Response Workflow

### tj-actions: identify exposed executions before rotating everything

StepSecurity's **March 14, 2025** report describes a compromised action downloading a Python script that attempted to extract sensitive data from runner memory. Its investigation attributed the initial access to a compromised `tj-actions-bot` personal access token, while stating that the method of obtaining that token was unknown. It observed leaked secrets in public build logs; importantly, absence of observed network exfiltration did not make publicly readable logs safe. [13]

The response advice included rotating discovered secrets and deleting affected workflow runs after rotation. The project's advisory was published **March 22, 2025**. These are different source dates, not interchangeable incident timestamps. [13][9]

This case identifies concrete users and handoffs: a CI/platform engineer identifies affected workflows and execution context; a cloud-IAM responder determines obtainable roles; credential owners coordinate replacement; the incident commander records assumptions and unresolved exposure. These are proposed workflow roles, not evidence of product demand from interviews.

The valuable output is therefore not another vulnerability list. It is an answer to: **Which executions could expose which authorities, which credentials might survive containment, and who must act next?** Static files help bound possibilities, but cannot establish which action revision ran, which token was issued or whether a secret was read.

### Drift: persistent downstream access is a separate problem

Google Threat Intelligence's Salesloft Drift investigation, dated **August 26, 2025**, provides a complementary token-theft case. It concerns downstream SaaS access, not a GitHub-to-AWS OIDC exploit, and should not be presented as evidence of that specific attack chain. [20]

Its relevance is architectural: terminating an upstream execution context is not the same operation as invalidating credentials obtained through it. Use these incidents to validate a response model, while retaining runtime and provider evidence as separate inputs rather than pretending static reachability proves compromise.

**Decision:** Begin with responders reconstructing a known CI incident, not a generic enterprise inventory buyer. Validate the proposed handoffs with real analysts before treating them as established purchasing behavior.

## GitHub and AWS Semantics Set the Safety Boundary

GitHub's OIDC reference documents audience and subject conditions, including repository, branch, tag and environment context. An environment-bearing subject must not automatically be interpreted as a branch restriction. Environment approval and deployment restrictions also require configuration evidence beyond the workflow's environment name. `id-token: write` enables requesting an OIDC token; it does not itself authorize AWS access. [6]

A credible model must also account for workflow/job permission overrides, event context, untrusted checkout or inputs, reusable workflows and local actions. Missing repository settings, environment protections or remotely referenced action implementations should produce an unresolved prerequisite, not an assumed safe or unsafe edge. GitHub also warns that transformed secret values are not guaranteed to be redacted. [4]

On AWS, distinguish the role's **trust policy**, which governs assumption, from authorization to use the resulting session. AWS documents that session policies intersect with the role's identity-based permissions and cannot expand them. A complete evaluator must additionally consider resource policies, explicit denies, permissions boundaries, organization controls and request conditions; it must not simplify every policy relationship into the same intersection operation. [19]

AWS's `AssumeRole` documentation specifies a default **3,600-second** session and a configured maximum between **one and 12 hours**; role chaining is limited to **one hour**. These are documented `AssumeRole` semantics, not a universal lifetime for every credential encountered. Actual session expiration remains unknown without issuance evidence. [19]

| Credential class | What the package should represent | Containment consequence |
|---|---|---|
| GitHub job credential or OIDC assertion | Job/issuance context; assertion validity if evidenced | Prevent further issuance; do not equate assertion expiry with downstream-session expiry |
| AWS STS session | Issuer, role, session-policy constraints and known or bounded expiration | Canceling CI is insufficient; evaluate session denial and expiration |
| Persistent credential or retrieved secret | Reference, owner and downstream authority; lifetime may be unknown | Disable, revoke or rotate at the authority that validates it |

These classes describe survival, not proof that credentials were stolen. GitHub documents job-specific OIDC issuance, while AWS documents a separate session and revocation mechanism. [1][19][17]

AWS revocation attaches `AWSRevokeOlderSessions`, denying actions for sessions issued before a cutoff. Later sessions are unaffected; the console procedure includes approximately **30 seconds** of future coverage for propagation. Service-linked roles and IAM Identity Center permission-set roles have documented exceptions or different procedures. [17]

**Decision:** Recommend separate controls for stopping new sessions, denying existing sessions and replacing persistent credentials. Never label a hypothetical policy change "contained" without stating its scope and assumptions.

The strongest directly documented overlap is BloodHound's GitHub graph and OpenHound's reproducible collection/conversion architecture. The extension identifies OpenHound as its supported primary collector and GitHound as an alternative; these are related paths, not three unrelated products. [3]

### OpenHound challenges the proposed architecture most directly

OpenHound uses DLT, stores raw resources before graph conversion and can use DuckDB for preprocessing and permission lookups. Its repository records an **Apache-2.0** licence, creation on **April 13, 2026**, and **104 commits** in the inspected snapshot. Those facts establish visible implementation activity, not production adoption or a verified latest release. [10]

An offline tool should therefore compete on a different decision: accepting already available, potentially incomplete source artifacts and producing defensible incident actions without collection credentials. OpenHound remains better suited when the organization can obtain supported provider data and wants BloodHound integration.

Cartography's inspected repository documents **Apache-2.0**, creation on **February 27, 2019**, and **2,277 commits**. Again, commit count is maintenance history, not user count. Its infrastructure-to-Neo4j architecture is substantial inventory prior art. [23]

### Scanners and policy tools should become inputs, not straw competitors

Checkov explicitly supports both Terraform files and JSON plans. Producing a plan is a separate operation: the proposed tool should consume a supplied plan rather than execute Terraform or providers itself. [15]

PMapper and Access Analyzer address a harder authorization problem than matching IAM action strings. zizmor and poutine address CI-specific weaknesses that a new parser should not casually reimplement. IAMbic's Git workflow also means that "diff" alone is not differentiation: the proposed distinction must be an evidence-aware change in potential reachability and credential survival.

For GitHound, PMapper, IAMbic, zizmor, poutine, Prowler, Checkov and Trivy, a complete **release-date, licence and latest-version audit was not established** in this investigation. No adoption figure or current-release claim is justified. For Astrix and Entro, public capability descriptions remain vendor evidence, not independent demonstrations of incident outcomes.

**Decision:** Use existing findings and graph formats where practical. Validate missing semantics with executable test fixtures before concluding that a competitor lacks them.

## An Evidence-Constrained Incident Package Has a Useful Narrow Scope

Consider a compromised deployment job that can request OIDC, assume a deployment role and potentially read a credential store. A useful report should distinguish "workflow requests role," "trust conditions potentially match," "policy permits candidate access" and "runtime use unknown." A secret reference must never be treated as a secret value or as proof of retrieval.

Each edge should carry its source artifact, location, snapshot identity, interpretation rule, prerequisites and unresolved conditions. HCL with unresolved variables, Terraform plan unknowns, missing organization policies and unavailable action implementations should remain visible uncertainty. Avoid numerical confidence scores unless calibrated against analyst judgments.

**Input safety is a product requirement.** Terraform state and plans can contain sensitive values. Prefer sanitized exports or allowlisted metadata extraction; never emit raw state, arbitrary string values or secret material. Do not run scanned actions, shell scripts, Terraform providers or external data sources. Network enrichment should be outside this tool's stated contract.

A proposed response sequence is:

1. Preserve non-secret evidence and identify affected executions and owners.
2. Stop the compromised entrypoint and block new token/session issuance.
3. Deny affected existing sessions where appropriate.
4. Disable or rotate potentially exposed persistent credentials, coordinating dependent consumers.
5. Restore narrowly scoped access and verify through separately authorized operational procedures.

This is a dependency-aware recommendation, not a universal rigid order. Urgent revocation can precede service migration; other credentials require replacement before invalidation to avoid an outage. AWS's older-session mechanism demonstrates why an issuance block and a session-denial step must remain separate. [17]

Snapshot comparison should classify changes as configuration changes, evidence changes or parser/model changes. A missing edge after an incomplete export must not appear as successful remediation. Hypothetical containment should report **"this modeled path is removed under these assumptions"**, not "the attacker is evicted."

**Decision:** Make the deliverable a portable case file with source-linked paths, survival classes, owner tasks, unresolved questions and reversible hypothetical changes.

## Synthesis: Four Directions Worth Testing With Analysts

Across mechanism, scope and trade-offs, the alternatives separate cleanly: BloodHound/OpenHound and Cartography organize collected relationships; PMapper and Access Analyzer deepen authorization analysis; scanners identify source-level weaknesses; IAMbic governs changes; connected NHI platforms seek operational context. Their advantages depend on collection, policy coverage or integrations. The offline proposal exchanges that context for a smaller access footprint and reproducible artifact analysis.

The non-obvious tension is that **more conservative output can be more useful during response**, but only if uncertainty is actionable rather than overwhelming. Conversely, a precise-looking graph assembled from incomplete state can be less trustworthy than a simpler checklist.

1. **Evidence-Bound CI-to-Role Case File.** Build source-linked potential paths with explicit missing prerequisites and OpenGraph-compatible export. Compare against BloodHound/OpenHound, Cartography and PMapper on identical public or synthetic fixtures. Have CI and cloud responders assess explanation correctness, missing assumptions and time to a defensible scope decision.

2. **Credential-Survival and Response Dependency Planner.** Separate job credentials, independently expiring sessions and persistent downstream credentials. Test cancellation, trust-policy changes, older-session denial and downstream rotation with incident commanders and service owners. Compare resulting plans with NHI-platform demonstrations and existing runbooks; record unsafe recommendations and operational disruption, not just task completion speed.

3. **Evidence-Aware Snapshot and Containment Review.** Show which paths changed because permissions changed versus evidence disappeared. Test incomplete snapshots, reordered Terraform output and parser upgrades against IAMbic-style Git review and graph workflows. Analysts should identify false "fixed" findings and explain what additional evidence would resolve them.

4. **No-Execution, No-Secret Incident Intake.** Accept sanitized YAML, local-action metadata, IAM JSON and Terraform artifacts in a disconnected workflow. Compare ingestion and findings with zizmor, poutine, Checkov/Trivy and Prowler. Validate zero network activity, zero scanned-code execution and no sensitive-value output, then test whether responders can actually supply sufficiently complete artifacts.

These are testable product hypotheses, not demonstrated uniqueness. The strongest validation is a blinded case exercise with real responders, followed by analysis of disagreements and missing evidence.
