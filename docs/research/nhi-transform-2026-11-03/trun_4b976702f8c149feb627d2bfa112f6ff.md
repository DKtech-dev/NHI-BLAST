# Containment Decisions Without Cloud Access: Precise Prior Art

## Executive Summary

**Assessment cutoff: 2026-11-03.** This is a source review, not a product-conformance test or user study.

- **Graph Prior Art Is Substantial**: BloodHound already computes GitHub access gates; Cartography already links GitHub repositories to observed AWS OIDC role use. A cross-system graph alone is not differentiation.
- **Session State Is The Important Boundary**: A workflow's configured session, an attacker-mintable session, and credentials already carried by an attacker require different reasoning.
- **Rotation Is A Dependency Problem**: Replacing a credential before removing its exposure path can disclose the replacement. Original incident responses establish the operational problem, not demand for a particular product.
- **Completeness Must Affect Conclusions**: Missing workflows, unavailable policies and failed parsing cannot become evidence that containment succeeded.
- **Existing Engines Have Advantages**: Use established GitHub analysis, IAM reasoning and formal policy comparison where appropriate; do not casually reproduce them.
- **Recommended Starting Point**: Build a local containment worksheet with credential-state tracking and ordering counterexamples, not another general-purpose graph platform.

## 1. Model Typed Paths And Separate Credential States

A useful path is not one undifferentiated `CAN_ACCESS` edge:

```text
Compromised entrypoint
  -> ControlsExecution(job/step)
  -> MayRequestOIDC(claim constraints)
  -> TrustMayMatch(role)
  -> MayObtainSession(role, issuance constraints)
  -> MayCall(action, resource, request context)
  -> MayReadCredential(version or store)
```

Each edge needs source location, artifact identity, parser/rule version, assumptions, missing evidence and an explanation. **Possible access, observed issuance, observed secret exposure and confirmed attacker use must remain separate.**

The GitHub side includes event eligibility, effective job permissions, environment gates, reusable workflows and local-action resolution. `id-token: write` enables requesting an OIDC token; it does not itself grant AWS resource permissions. AWS guidance uses audience `sts.amazonaws.com` for the official credentials action and recommends checking `sub`. An environment-based subject names the environment, not the branch; branch restrictions then require appropriate environment protection. YAML alone may not establish those remotely configured protections. [42][446.16-17][446.25-28][446.38-40]

The AWS side must distinguish **trust to assume a role** from **authorization after assumption**. Identity policies, resource policies, explicit denies, boundaries, session policies and applicable organization controls do not reduce to one universal intersection formula. AWS documents both union and intersection behavior depending on policy type and context. Unsupported combinations should produce unresolved conditions, not invented certainty. [29][444.652-662]

**Configured versus attacker-mintable sessions.** Suppose an action requests 900 seconds and voluntarily supplies a restrictive session policy. If the compromise permits arbitrary code in that OIDC-enabled job, the attacker may request a different permitted duration or omit that voluntary restriction. Model the enforced trust, role maximum and other applicable constraints, not merely action inputs. `AssumeRoleWithWebIdentity` does not require pre-existing AWS credentials; its default session is one hour, with duration bounded by the role configuration. Ordinary role chaining has a separate one-hour maximum. [22][328.20-25][328.34-37][330.95]

**Carried credentials versus future issuance.** Removing an issuance edge must not delete an already-issued credential from the model. Without issuance metadata, report possible sessions and expiry bounds, not an exact expiration time.

| Credential state | Relevant termination mechanism | Containment implication |
|---|---|---|
| Job-bound `GITHUB_TOKEN` | Job completion or effective maximum lifetime | Do not apply its lifetime to PATs or AWS sessions. [40][445.11] |
| Already-issued AWS STS session | Expiry, effective policy changes, applicable session revocation | Canceling CI is not sufficient evidence of AWS containment. |
| Persistent key, PAT or signing credential | Issuer-side invalidation, expiry or replacement | Deleting its CI copy does not invalidate a stolen copy. |

AWS evaluates temporary-credential permissions on subsequent requests. Its role-session revocation procedure denies sessions issued before a cutoff; later sessions are not covered. Thus both **existing-session access** and **future issuance** need attention. Resource-policy grants can require an explicit deny rather than merely removing an identity-policy allow. [28][329.538][327.648-654]

### The important implementation distinctions

**BloodHound already goes beyond raw permissions.** Its computed branch-access logic evaluates merge/push gates and actor-specific allowances. The schema includes `GH_CanAccessSecret`, `GH_CanDeployToEnvironment` and `GH_CanAssumeIdentity`. However, a generic identity edge does not establish complete AWS policy evaluation: the inspected GitHound `Parse-GitHoundOIDCSubject` specifically consumes Azure federated identity credentials. [37][425.223-236][424.72-90][509.451-465]

**OpenHound already provides reproducible collection architecture.** Raw collection precedes conversion. Its GitHub documentation explicitly acknowledges incomplete scopes after retries, skipped dynamic workflow paths and missing workflow files. These are valuable prior-art requirements, not omissions to rediscover. Its PAT inventory is documented as not containing plaintext PATs. Separately, GitHound's inspected secret-scanning code can use an exposed PAT in a live GitHub request; that collection behavior is incompatible with this proposed runtime contract. [12][208.49-53][208.81-83][509.407-408]

**Cartography's release matters.** Version **0.144.0** source annotates conditional trust, preserving condition information instead of resolving it against a nonexistent request token. An older inspected `master` excerpt's “TODO support conditions” is therefore not a fair description of that release. Its GitHub schema already includes `ASSUMED_ROLE_WITH_WEB_IDENTITY` to `AWSRole`, with observation timestamps and counts. [51][507.80-85][202.676-683]

A separate permissions-mapping document says conditional `Deny` is treated as absolute deny. **Inference:** importing such edges unchanged could understate potential reachability; it is not automatically a conservative may-access model. Also, absence of observed use is explicitly limited by collection windows and event coverage. [39][422.62-63]

**PMapper is not merely an identity-policy checker.** Inspected code handles optional resource policies, SCP groups, boundaries and session policies. Its graph-search comments explicitly discard the supplied session policy after checking the starting principal, assuming it does not affect edge accessibility. That assumption must not silently become a general model of already-issued sessions. [44][508.97-121][508.42][508.48]

**Scanner boundaries matter.** At `v1.30.1`, zizmor documents no code execution, explicit offline operation, and `--strict-collection`; it does not analyze arbitrary referenced script files. Poutine's documented default version check means “local analysis” is not synonymous with “no network.” Disabling that check removes that mechanism, not proof of a complete network audit. [15][212.383-413][211.98-104]

**AWS already supplies semantic policy comparison.** `CheckNoNewAccess` returns PASS for no new access; FAIL means the update *might* allow new access. Zelkova's SMT-based permissiveness reasoning is stronger prior art than textual policy diff, but neither establishes containment of an entire GitHub/session/credential chain. The paper is AWS-authored research, not independent comparative performance evidence. [1][195.26-29][195.66-68]

Commercial NHI marketing establishes neither this precise offline contract nor its temporal semantics. **Entro/Astrix capability for this package remains U**, not absent. No comparative adoption or performance conclusion follows.

## 3. Incident Reports Establish Concrete Analyst Work

These are original operational accounts, not interviews or usability measurements.

| Original incident/response | Actual work documented | Requirement justified |
|---|---|---|
| **Codecov, detected 2021-04-01** | A customer found a checksum mismatch. An HMAC key extracted from a Docker layer enabled uploader modification; the payload extracted environment variables and repository information. Codecov revoked the key and rotated production keys. | Trace publishing authority into executable CI dependencies and downstream credential exposure. [4][199.20-22][199.36-44] |
| **CircleCI, alert 2023-01-04** | Responders needed a secrets inventory and issuer-side rotation. A **2023-03-13** tool update addressed secrets not visible in ordinary inventory. | Model incomplete inventories; distinguish removal from CI from invalidation at the source. [25][324.130-131][323.51] |
| **HashiCorp's CircleCI response, 2023** | It analyzed connected repositories and rotated stored or connected secrets. Windows signing-key revocation occurred **2023-01-05**; an Apple certificate's later revocation was confirmed **2023-04-24**. | Include availability, consumer migration and staged revocation, not one universal “rotate now” command. No confirmed HashiCorp compromise should be inferred. [27][325.13-25][325.47-50] |
| **reviewdog, 2025-03-11, 18:42-20:31 UTC** | A compromised contributor PAT was identified as the credential used to overwrite the action tag. Maintainers restricted writers and disabled automated invitations. | Contain publishing/control-plane access, not only downstream secrets. Public activity omissions are not proof of no tag change. [2][196.126][196.52-54][196.184-185] |

The likely users are incident commanders coordinating platform owners, cloud responders validating authorization, and service owners migrating consumers. The package should answer: **what may still work, what must change first, who owns it, and what evidence is still required?** Willingness to use or buy such a package remains unknown.

Rotation should be a **partial order with emergency overrides**, not a supposedly optimal universal sequence:

1. Preserve evidence while quarantining compromised execution and publishing authority.
2. Block future issuance; separately deny or revoke relevant carried sessions and direct grants.
3. Repair credential-read and write-back exposure paths.
4. Replace credentials at their issuer, migrate clean consumers, invalidate old versions and record verification tasks.

Availability-sensitive exceptions need explicit approval. Active exploitation may justify immediate revocation before orderly migration.

Three **hypothetical counterexamples**, not claims about those incidents:

- A replacement secret injected into an unchanged malicious uploader is stolen again.
- Removing OIDC trust leaves a carried STS session able to read the replacement secret unless its effective access is also contained.
- Updating a CI variable while leaving the issuer's old API key valid preserves attacker access.

## 4. Completeness, Conservative Diff And Runtime Architecture

Every source needs a manifest: scope, capture time, ref/version, expected and parsed objects where knowable, errors, skips, unresolved references and missing policy layers. File counts alone do not measure semantic completeness.

Examples include missing reusable workflows, runtime-generated matrices, unavailable environment settings, uncollected accounts, unknown Terraform values and unsupported IAM conditions. Terraform plans contain only a partial representation of final values; a fully represented state is still not proof of current deployed reality. Plans and state can contain secrets even when values are marked sensitive.[515.0-5]

**Safe snapshot comparison requires comparable coverage.** If snapshot B lacks a policy or fails to parse a workflow present in A, the result is “visibility decreased,” not “path removed.” Keep separate:

- configuration change;
- changed potential reachability;
- carried-credential residual risk;
- missing or contradictory evidence.

A proposed edit can mean “blocked under this model and these assumptions,” never “deployed” or “attacker access revoked.” Test the invariant that removing evidence cannot increase containment assurance. Standards offer useful precedent: SLSA VSA distinguishes an empty dependency claim from an unset claim, and records verifier, policy and input evidence metadata. This is a design analogy, not an incident-response standard. [48][12.0]

| Architecture | Advantage | Boundary |
|---|---|---|
| **Local static artifacts** | No collection credentials or runtime cloud access | Intent may differ from deployment; runtime state is unknown |
| **Offline collected snapshots** | Can include organization settings and observations | Acquisition happened elsewhere; age, permission gaps and sanitization matter |
| **Live services** | Can obtain fresher evidence and execute changes | Outside the strict runtime contract; still necessary for operational verification |

Start with an in-memory graph, versioned JSON evidence package and static HTML report. No SaaS or database is justified for the first bounded incident workflow; optional OpenGraph export supports existing investigations.

Enforce no network at the OS boundary. Never execute workflows, local-action code, shell, Terraform providers, `init`/`plan`, remote-module retrieval, repository plugins or repository-supplied rules. Parse pre-exported JSON and a bounded HCL subset; unresolved computation stays unknown.

Discard secret-value fields before logging or persistence; retain identifiers, source locations and credential-version metadata, not values or value hashes. **Important limitation:** reading an unsanitized state file can transiently encounter secrets in memory. If “never encounter secret bytes” is required, accept only an upstream-sanitized projection. Do not retain raw input copies, value-bearing source snippets or crash dumps.

## 5. Four Feasible Directions And A Falsifiable Recommendation

These rankings are engineering judgments, not measured market results.

| Rank | Direction | Operational value / evidence / implementation risk | Validation against prior art |
|---|---|---|---|
| **1** | **Containment worksheet**: credential-state ledger, prerequisite actions and re-exposure counterexamples | High / strong incident evidence / moderate | Compare with official runbooks plus analysts' current spreadsheets and graph tools |
| **2** | **Coverage-aware snapshot and hypothetical-change review** | High / strong technical rationale, unmeasured user benefit / moderate | Compare with IAMbic/Git diffs and Access Analyzer policy checks |
| **3** | **Typed GitHub-to-AWS evidence bridge**, with OpenGraph export | Potentially high / substantial prior art / high semantic risk | Compare with BloodHound computed edges, Cartography and PMapper, including unsupported-condition cases |
| **4** | **Public incident replay and regression packs** for containment decisions | Focused / moderate / low-to-moderate | Compare with existing policy/scanner tests; require explicit empty-suite and missing-input failures |

**Recommend direction 1**, initially with analyst-confirmed links and narrowly supported authorization semantics. It tests the decision-support hypothesis without first building a complete IAM solver.

Run a counterbalanced study with approximately **12 working responders and six synthetic cases derived from public incidents**. Compare against the best practical combination of existing tools and official procedures, not a deliberately weak baseline. Measure input-preparation time separately.

Proposed success thresholds, **not observed results**:

- At least **25% lower median time** to a correct, reviewable containment plan, including preparation.
- At least **90% correct** credential-state and prerequisite decisions against expert-adjudicated answers.
- **Zero high-severity re-exposure recommendations** in the test cases.
- Every injected parsing/coverage failure produces an explicit unresolved result, never false containment.
- Zero network attempts, scanned-content execution or persisted synthetic secret sentinels under instrumentation.

The value hypothesis fails if preparation consumes the savings, existing worksheets perform equivalently, analysts cannot act without live evidence in most target cases, or the package increases false assurance. Production accuracy, adoption, performance and willingness to pay are **unknown**.

## 6. Synthesis

Existing solutions already provide stronger starting points for broad GitHub relationships, collected cloud observations, local IAM inference, managed configuration changes and formal policy comparison. A new product should interoperate with them rather than claim to replace them.

The plausible differentiation is **the combination** of typed evidence, separate issuance/carried-credential state, replacement prerequisites and coverage-conservative handoff under a strict local runtime contract. Neither novelty nor superiority is established. The first deliverable should be a reviewable containment decision package whose uncertainty is visible, not a graph that implies knowledge it does not possess.
